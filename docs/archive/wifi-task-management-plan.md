# Wi-Fi 任务管理实施方案

日期：2026-11-14。状态：设计提案，尚未实现本文新增业务。

基线：用户已确认车机与 UGV 分离、启动及诊断两步完成；沿用现有 Mesh-Lite、独立设备身份、mTLS、MQTT ACL、USB 转发及 list/ping/status/echo。本文只整理下一阶段方案，不运行固件 build、烧录或修改现有业务代码。

## 2. 部署和职责

### 2.1 当前部署

```text
车机终端程序（独立仓库）
  │ USB 串口：请求、响应、后续业务事件
root C6，pc-root-001，Mesh 第 1 层
  │ Wi-Fi / MQTT over TLS
UGV C6，ugv-001，Mesh 第 2 层
  │ USB 多路字节隧道，仅转发到本地 Broker
模拟 Jetson 的电脑
  ├─ Mosquitto：认证、主题权限、消息分发
  ├─ ugv_service：任务、调度、状态、事件、车机接口
  ├─ SQLite：任务、操作、进度、结果、事件、证据索引
  └─ 执行/分析/媒体适配器：接入后提供实际业务能力

UGV C6 ← Wi-Fi → UAV C6，uav-001，第 3 层
                         ├─ Wi-Fi → micro-001，第 4 层
                         └─ Wi-Fi → micro-002，第 4 层

应用层：root、UAV、两个 Micro 各自连接 UGV 入口并与 Broker 建立 TLS。
Micro 的 MQTT 目的服务仍是 UGV，Wi-Fi 多跳路径经过 UAV。
```

root 继续通过服务发现使用 UGV STA 入口；UAV/Micro 使用当前可达的 UGV SoftAP 入口。IP 地址以发现及实际日志为准，不硬编码示例地址。

当前 UGV C6 是通信网关；任务服务在模拟 Jetson 的电脑上。UGV 自身执行任务由电脑上的本地执行适配器处理，之后原样迁移到 Jetson；不能因为 UGV C6 不在 MQTT 客户端列表中而漏掉 ugv-001 的业务档案。

## 3. 业务对象、能力和状态

### 3.1 统一对象

- Mission：用户层目标，如一次露营勘察或某时段园区巡防。
- Task：一个可分配、可跟踪的执行单元，包含 task_id、mission_id、父任务/依赖、类型、目标节点、配置版本、优先级、截止时间和完成条件。
- Command：一次具体操作，如提交、开始、暂停、恢复、取消、修改配置；使用独立 command_id。一次任务可包含多个操作。
- Event：一个疑似异常/告警，包含 event_id、来源、防区、位置、风险、观测和复核结论。
- Evidence：照片、片段或其他文件的索引，关联 mission/task/event、来源、采集时间、位置、文件类型、大小、哈希及存储位置。
- Result：候选点、评价依据、路径、复核结论等结构化输出，记录输入证据、处理模块/版本和人工修订。

任务、异常事件和媒体会话分别记录状态。任务取消不自动清除告警；用户已读也不代表异常解除；照片文件传完也不代表选址分析完成。

### 3.2 能力模型

在原有 ping/status/echo 之外，逐项公告执行能力及限制，例如 survey、patrol、verify、navigate、photo.capture、video.preview、image.analyze、event.review。每项包含 supported、available、适配器版本及约束；暂停、在线更新和安全取消也是需要单独声明的能力。

- pc-root-001 默认是车机通信端点，不自动成为勘察执行器。
- ugv-001 对应 UGV 业务服务和地面/分析适配器。
- uav-001 对应普通无人机能力档案，高清相机/云台接通后才公告高清复核能力。
- micro-001/micro-002 为独立设备，各自记录载荷、续航和区域任务能力；不能根据 micro_uav 角色直接认定其有摄像头或定位能力。

保持所有角色通用注册、独立身份和证书机制。新设备经受控注册、证书认证、ACL 更新和新鲜能力/状态校验后，自动进入候选执行器集合，不硬编码上述编号。

ready 表示通信可用；任务还要检查业务能力、资源和数据新鲜度。位置、电量不可得时传 null 及原因，不生成假值，也不参与要求这些输入的自动调度。

### 3.3 任务状态与两级确认

```text
CREATED → QUEUED → DISPATCHING → ACCEPTED → RUNNING → SUCCEEDED
                                  │           ├─ PAUSE_PENDING → PAUSED → RUNNING
                                  │           ├─ CANCEL_PENDING → CANCELLED
                                  └───────────┴─ FAILED
```

- REJECTED：权限、配置、能力、资源或状态不满足，给出原因。
- EXPIRED：尚未执行的任务超过允许开始时间。
- 已执行任务超过完成期限：记录 deadline_missed，按已确认策略请求停止或继续，不能凭时钟推断已经停止。
- 链路状态单独为 online/offline；执行状态无法确认时标记 RECONCILING/UNKNOWN 并保留最后已知状态。
- 配置更新先生成新 revision，执行器明确应用后才改变 active_revision；不支持在线更新时拒绝或要求先暂停。
- 取消/暂停的成功由实际执行器确认；失联时保持 pending，不能只改车机显示。

三类确认分开记录：UGV_RECEIVED（校验通过并入库）、NODE_ACCEPTED（执行器接受任务）、EXECUTION_RESULT（完成/失败/取消及输出）。MQTT PUBACK 不替代这三类业务反馈。

### 3.4 调度第一版

先做“人工指定 + 基于规则的候选推荐”：过滤在线/能力/载荷/位置和电量约束，检查资源占用，再按优先级、截止时间、排队次序分配。每个物理运动执行器默认一个活动任务；分析与采集可按资源独立并发。

支持任务依赖和复核插单；只有适配器声明可暂停/交接时才抢占。失联且原执行器是否仍在运动未知时，不直接重复派发相同运动动作。路径规划算法作为独立适配器：第一轮可由人工提供合法区域/航点，记录坐标系、单位、禁入规则及配置版本。

## 4. 两个场景及全部车机业务映射

### 4.1 露营勘察

```text
车机创建 survey Mission，提交区域、约束、目标节点或请求推荐
  → UGV 保存并分解采集任务
  → 能力满足的 UAV/Micro 接受、开始、上报位置与阶段进度
  → 原始采集资料归入 UGV 媒体服务
  → 分析适配器输出候选点、排序、依据、证据及可用路径
  → 车机选择候选点，创建关联 verify Task
  → 实际执行器复核/补拍，UGV 汇总结果和证据
  → 必要输出齐备后 Mission 完成
```

候选点包含坐标与精度/来源、可观测特征、禁入/风险标记、评分规则版本和关联证据。到达路径区分“已由模块生成”与“用户提供”；没有足够输入时标记未知/待确认。分析模块缺失、输入不足或画面不可用时，不能输出伪造的安全选址结论。

### 4.2 园区巡防/露营安防

```text
车机创建 patrol Mission，配置防区、周期及规则
  → 两个 Micro 按各自能力执行区域初筛并回传进度/观测
  → 每条有效疑似线索立即生成 Event，不等待全区巡查结束
  → UGV 派发普通 UAV 高清复核任务，引用同一 event_id
  → 上报确认异常/解除疑似/无法确认，并关联高清证据
  → 按需调用地面核验接口或请求人工处置
  → 车机已读、确认、误报反馈或进一步复核
  → 保存处置回执、复核结论和事件关闭理由
```

事件独立记录 observation（suspected/confirmed/false_alarm/inconclusive）、处理状态（new/acknowledged/in_progress/resolved）及用户反馈。复核失败/目标离开/照片模糊时为待确认，不能当作解除误报。重复观测按来源、时间、区域与目标线索关联，保留原观测，不简单按事件类型合并。

### 4.3 车机接口清单

下列名称为建议接口，当前 CLI 尚不支持。

| 车机发送 | 建议接口及反馈 |
| --- | --- |
| 创建/开始/暂停/恢复/取消 | task.submit、task.control；返回入库确认、执行器确认与状态变更 |
| 区域、航点、优先级、截止时间修改 | task.update；expected_revision 校验，返回接受/应用结果 |
| 拍照、补拍、开启/停止预览、取证 | media.request；由适配器执行并返回文件/会话与实际状态 |
| 异常复核或处置 | 创建 verify/response Task，引用 event_id 和证据要求 |
| 已读、确认异常、解除误报、请求再核验 | event.feedback；记录操作者、理由、版本并回传事件更新 |
| 节点/能力/服务/任务查询 | nodes.query、services.query、task.query；支持分页和更新时间 |
| 车辆位置/GNSS/IMU | location.update；携带坐标系、单位、精度/质量、数据来源与采样时间 |

| 车机接收 | 建议事件或查询结果 |
| --- | --- |
| 身份、能力与服务可用状态 | node.changed、service.changed；UGV 汇总可信登记信息 |
| 位置、电量、运行及在线状态 | node.status；包含采样时间、UGV 接收时间和过期标记 |
| 接收/执行/进度/结果 | task.received、task.accepted、task.progress、task.finished |
| 候选点、评价依据、路径 | result.available；小型摘要及分页详情/证据引用 |
| 初筛、复核与待确认结论 | event.updated、result.available；同一事件关联全部阶段 |
| 告警及反馈处理结果 | event.raised、event.updated、feedback.received |
| 缩略图、高清照片、片段、预览 | evidence.available、media.state；数据传输按独立媒体路径 |
| 链路/失败/延迟/吞吐及路径变化 | network.status；标记测量层次、窗口与数据来源 |

车机请求默认异步：短时返回持久化确认，后续订阅事件。车机重连用事件游标/任务版本补齐，不能只靠在线推送；旧响应不得覆盖较新状态。

## 5. 协议、消息大小与传输

### 5.1 消息约定

保留现有诊断消息；新增业务消息采用统一字段，发布协议文档及样例，并同步升级车机、root 转发、UGV 路由及执行器校验。现有固定白名单不会自动接受新业务。

| 字段 | 约定 |
| --- | --- |
| v、type | 明确业务协议版本及 task.submit 等消息类型；与 MQTT 协议版本分开 |
| msg_id | 单条消息标识；同一请求的重传保留标识，冲突内容拒绝 |
| node_id、target | 沿用当前命名表示源与目标；源必须绑定认证主题/本地可信上下文 |
| mission_id、task_id、event_id | 按业务需要携带；task_id 在首次提交前生成，便于超时后查询 |
| command_id | 一次业务操作的稳定标识，执行器去重；与任务标识分开 |
| ts_unix_ms、expires_unix_ms | UTC 毫秒及命令有效期限；任务的执行截止时间单独存储 |
| revision、state_seq、boot_id | 配置版本、状态更新序号、执行器启动标识，用于防旧更新与重启对账 |
| payload | 有界业务内容或完整配置/结果的引用 |

跨设备观测使用带同步质量的 UTC；本机持续时间、超时使用单调时间。uptime_ms 继续表示本设备本次启动后的运行时间，不用于直接比较两台设备的采集时刻。

### 5.2 当前路径的实际限制

已核对源码：车机/执行器命令目前最多 512 字节，串口 JSON 帧最多 1024 字节，UGV 请求有效期校验窗口最多 60 秒。完整区域、多航点、长结果可能超限，不能直接塞进现有 echo 或扩大所有缓冲区。

第一轮增加有界配置分块：upload.begin → upload.chunk → upload.commit。块带 upload_id、序号、数量；服务校验总长度、数量、过期、完整性哈希、坐标及字段后原子提交。任务通过 config_id/hash 引用已提交配置。下发到 C6 的配置也按能力和容量分块；限制最大活动配置和航点数，超限拒绝。查询结果继续分页。每个实际编码包都检查字节数，不能按字符数估算。

命令 TTL 与任务时长分开：一条提交命令可在短窗口内有效，但巡防可持续较长时间；任务对象有自己的开始窗口/截止时间和停止策略。现有 60 秒请求窗口不应限制整个 Mission 的执行时长。

### 5.3 MQTT 主题和权限

尽量复用已有已认证的车机 requests/responses 入口，增加业务路由；新增车机 events 通知入口和每节点 task_commands/task_events 入口，并同步升级 root 转发、订阅和 Broker ACL。以下为建议：

```text
mesh/v1/terminals/<car-id>/requests
mesh/v1/terminals/<car-id>/responses
mesh/v1/terminals/<car-id>/events
mesh/v1/nodes/<node-id>/task_commands
mesh/v1/nodes/<node-id>/task_events
```

- 车机仅写自己的 requests，读自己的 responses/events；服务端再校验任务及所属 UGV 的操作权限。
- 执行节点仅读自己的 task_commands，写自己的 task_events，不能跨节点控制或伪造其他来源。
- UGV 后台按管理范围发命令、收任务事件；UGV 本地执行器通过同一任务引擎的内部接口反馈。
- 操作消息 QoS 1、非 retained；重要进度/结果/告警持久化并可重放查询。高频普通遥测可用 QoS 0 和限频。
- 状态快照如使用 retained，必须带版本、时间及启动标识，仅作快照。任务动作禁止 retained。
- MQTT 3.1.1 即可承载本方案；命令到期由应用校验，不假设已启用 MQTT 5 特性。

### 5.4 照片与视频

| 数据 | 目标承载 | 当前阶段 |
| --- | --- | --- |
| 任务、状态、结果摘要、事件、回执、媒体控制 | MQTT over TLS over TCP | 当前路径可扩展 |
| 照片、深度图、证据文件、缩略图文件 | HTTPS/TLS 文件服务 | 先建媒体索引及存储接口；需另外打通设备与服务的实际文件路径 |
| 实时视频预览 | 适配后的 SRT/UDP 等媒体路径 | 当前 Broker 专用 USB 隧道不支持；待 IP 通路和收发端适配验证 |

当前 serial_tcp_bridge.py 只把 USB 通道转到固定本地 Broker，不是通用 IP 网卡；不能仅把 URL 写为 UGV:8443 就认定 HTTPS 可用。未来 S31 也要先验证 USB 网卡、IP 可达性和吞吐，再启用远程媒体功能。若在 C6 阶段提前需要少量文件，必须单独实现有授权、配额和流控的文件通路并实测，不能混入现有控制报文作为默认能力。

无媒体硬件时可从 UGV 电脑导入真实文件验收存储/查询/关联，明确标记 origin=imported，不冒充无人机采集。常态车机接收元数据/结果；可达的文件通路上线后再取缩略图、高清证据与预览。连续录像回传不列入第一轮。

media.request 必须进入真实媒体适配器。开启预览要区分 requested/starting/streaming，收到实际帧/接收统计后才为 streaming；停止后核对发送停止及资源释放；不具备摄像头/通路时返回 unsupported/media_path_unavailable。

## 6. 持久化、并发与断线恢复

UGV 使用 Python 标准库 SQLite，电脑与 Jetson 共用业务逻辑；业务模块放入可独立测试的包，tools/ugv_service.py 保持启动入口。数据库和媒体目录为运行数据，不提交 Git。

建议表：missions、tasks、task_operations、task_events、events、event_feedback、results、evidence、outbox、inbox_dedup、node_snapshots。任务当前状态和操作/待发消息在同一事务落盘，提交成功后才返回 UGV_RECEIVED。

MQTT 回调只做有界解析与入队。数据库写操作序列化，调度和执行反馈异步处理，图像计算在独立 worker 执行，不能长时间阻塞控制和心跳。按节点及资源限制并发，队列满必须明确反馈 busy，而不是悄悄丢请求。

任务管理不能沿用当前一次命令最多等待 10 秒的同步工作模式。增加后台任务派发器、持久化超时/重试记录及异步事件处理；避免一个失联执行器阻塞其他节点的控制请求。

故障处理规则：

1. 重复提交：用来源、task_id、command_id 和规范化内容哈希去重；相同内容返回既有结果，冲突内容拒绝。节点按 command_id/revision 拒绝重复动作。
2. 请求超时：车机先按 task_id/command_id 查询，再决定是否用相同幂等标识重试；不能生成新标识盲目再建任务。
3. USB/Broker/网络断开：记录离线并保持最后已知任务状态；按预先声明的本地执行策略处理，UI 显示更新时间及未知状态。
4. UGV 重启：恢复数据库，重新认证，查询执行器当前任务/启动标识/配置版本；完成对账后再派发。outbox 中的物理动作也要重新校验期限、版本和执行器状态，不能启动即清空重放。
5. C6 重启：重新登记；本地仅持久化必要的活动任务摘要、操作标识及关键阶段，控制写入频率。若无法证明动作是否完成，报告 UNKNOWN，不能宣称成功或自动重做。
6. 取消丢包/取消时失联：保持 CANCEL_PENDING；重连查询并补发仍有效的同一取消操作，最终以执行器停止反馈为准。
7. 终态幂等：完成结果、告警反馈、证据提交可重复接收但不重复入账；较旧 state_seq/revision 不回滚当前状态。

本方案追求可追踪、可恢复、可去重；MQTT QoS 或数据库事务本身都不能保证物理动作“恰好执行一次”。

## 7. 实施顺序与交付

### M1：可持久化的任务管理与真实节点反馈

- 冻结任务/能力/事件公共模型、错误码、状态迁移和接口样例。
- UGV 增加 SQLite 事务、幂等、异步派发、查询、进度、取消/暂停及重启对账。
- 车机增加任务提交/列表/详情/开始/暂停/恢复/取消/修改与 watch，保留旧诊断命令。
- C6 增加任务代理，UGV 增加本地适配器；新增任务主题、ACL 和注册约束。
- 首个实物执行任务可选 network_diagnostics：由真实 C6 在指定时长内采样链路和资源状态，返回样本/统计，验证管理闭环。它只验收任务基础设施，不等同于业务勘察。
- survey/patrol/verify 的参数、任务依赖及记录可以建立；缺少实际能力时拒绝开始。测试执行器必须显式标记 execution_mode=simulation，不能混为实物业务验收。

### M2：两场景编排、事件、结果和证据索引

- 实现 survey/patrol/verify 等任务模型、父子任务、依赖、初筛触发复核与人工反馈。
- 引入分析/路径/媒体适配器契约、候选点结果、事件状态及证据索引。
- 用可追溯的输入文件或明确模拟执行器验证两套完整流程；保留真实模块替换入口和数据来源。
- 完成独立车机事件补查与任务/事件/证据关联展示。

### M3：实际载具与媒体接入

- 接入相机/云台、飞控、地面运动、GNSS/IMU 及实际分析/路径模块；逐项启用能力。
- 将电脑上的 UGV 服务迁移 Jetson，验证依赖、数据恢复和性能。
- 验证 S31 网卡与 IP 通路后接入 HTTPS 文件和按需预览；媒体与控制独立限速、排队和背压。
- 真实完成露营采集分析复核，以及 Micro 初筛→UAV 高清复核→告警反馈；地面核验按跨项目接口接续。

### M4：弱网、负载和规模验收

- 在 Wi-Fi 多跳下分别测控制回执、进度、结果、文件与视频；明确包长、频率、跳数、负载和测量边界。
- 故障期间验证无重复物理动作、无虚假完成、无过期命令复活，媒体拥塞下优先保障控制。
- 当前五板验证独立任务和两个 Micro 并行，更多节点通过受控注册扩展。实物规模与仿真规模分开报告。

## 8. 验收清单

| 验收项 | 可观察通过条件 |
| --- | --- |
| 真实任务闭环 | 车机提交后返回稳定 task_id；UGV 重启仍可查询；真实执行器反馈 accepted/running/progress/result，非一次 echo |
| 设备与能力隔离 | 同时给两个 Micro 不同任务，状态/结果不串；缺少载荷或低质量必要输入时明确拒绝 |
| 三类确认 | 分别看到入库确认、执行器接受和执行结果，能解释在哪一阶段失败 |
| 暂停/取消/更新 | 支持的真实适配器确认行为；不支持则拒绝；失联时 pending；旧配置不覆盖新配置 |
| 幂等与故障恢复 | 重复包不产生重复任务/动作；Broker、USB、服务、执行器重启后对账；超时状态不被误报为成功 |
| 位置与进度 | 有来源、采样时刻、坐标系与质量；缺失为 unknown；过期值明确标注 |
| 露营场景 | 采集、分析、候选点、用户选择、复核和证据均关联同一 Mission；实物/导入/模拟来源可辨识 |
| 园区场景 | 单条初筛线索即可创建复核；统一 event_id；确认、误报、无法确认、人工反馈及处置回执分别留痕 |
| 媒体真实性 | 开启预览有实际数据与接收统计；无通路明确失败；照片哈希/时间/来源/任务与事件关联正确 |
| 安全 | 在实际 Broker 回归新增任务/事件主题 ACL；伪造来源、跨节点写入、越权反馈及过期命令被拒 |
| 资源与链路 | 用户编译后测分区与堆；控制/状态/媒体分项测量；不直接认定达到原表数值指标 |

建议下一次实施以 M1 为范围，首先完成任务模型、UGV 持久化引擎、节点代理和独立车机任务 CLI。相机/飞控/算法和媒体通路按适配器逐项接入；原有通信诊断能力持续保留。
